# 合同示例输入补全与定位查看修复

日期：2026-11-02；工作区 `aigc-image-review`，分支 `develop`。本轮未提交或合并。

## 用户看到的问题及根因

1. “查看疑似修改区域”原先只是阶段说明中的普通文字，没有点击处理。原图虽在页面上方，却不能从篡改结论直接打开。
2. “橙框：87个……需结合原图及字段复核”增加了无用的用户处理负担。
3. 示例合同2的“签署部分因输入截断未完整呈现，不能视为签署内容已核对”来自2026-10-31真实DeepSeek响应的warning，不是前端模板或人工手写文字。
4. 截断发生在 `buildSemanticPackage`，并非OCR漏掉签署区域：原始合同2有63个OCR块；旧批次块数上限100，合同1发出63块，合同2只能发出37块，止于“甲方”。后26块包含签署栏、电话、银行及帐号/税号标签，存在本地却没有发给模型。

旧输入的 `losses` 记录了 `m2:block_limit`。模型把此平台限制写入业务告警，前端又直接呈现，因此用户看到了系统自身的输入处理问题。

## 修改

- 橙框说明仅显示“疑似修改位置”。
- 篡改区提供真实按钮，打开当前材料的模态大图；支持50%–250%缩放、显示/隐藏标记、关闭和Esc退出。
- SEED框仍来自概率图阈值后的连通区域外接矩形，不是OCR文字框；前端按原图坐标等比显示。87是区域数量，不是人工确认的87个错误。
- 语义包总文字块上限从100调整到512，单材料上限256，保留原有总文本字符预算及隐私过滤，不无界发送。
- 版本更新为 `material-semantic-review/1.4`，新输入及审核指令参与缓存版本。
- 审核指令区分平台封装损失与材料实际缺项；不把输入截断、字段未纳入等内部说明拼入用户的业务告警；单文件不套用其他文件识别损失。
- 补全后合同1发出63个可发送块，合同2发出全部63块；合同1另有3块识别置信度不足、1块为空，仍保留真实过滤状态，未假装全部识别可靠。

## 实际复测与发布

两次重新运行师兄SDK流程，均实际调用DeepSeek，分别保存到平台根目录下：

- `runtime/replay/contract-evidence-20261102/`：补全输入后的第一轮，消除了签署栏截断，但解释中仍有内部处理说明。
- `runtime/replay/contract-evidence-20261102-v2/`：收紧面向用户的说明后再次执行；作为当前示例发布结果。

旧记录与首轮记录均保留。新例子读取真实响应，不在前端用字符串过滤伪装成重新核验。合同2现在说明9980元与大写200元不符，以及甲方名称差一个“市”字，warning与explanation中已没有“输入截断/未完整呈现”。单文件及跨文件3项均完成。

从原先12次累计到24次实际HTTP调用，本轮新增12次，仍在本任务50次上限内。预算台账继续使用 `runtime/replay/review-diagnostics-20261031/budget.json`，没有重置计数。

原始响应摘要仍保留模型的证据限制表达，双文件前端展示分事项结果，不把总摘要套作单文件说明。模型对第一份合同的数量标题理解仍需后续评估，本轮不能视作语义准确率全面验收。
