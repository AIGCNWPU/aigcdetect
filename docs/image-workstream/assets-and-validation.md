## 验证顺序

| 阶段 | 验证内容 | 应交付的证据 |
| --- | --- | --- |
| 资产 | 文件数、大小、哈希、来源和依赖兼容 | 下载账本、依赖锁、许可记录 |
| 加载 | 三个模型分别加载和单图推理 | 实际参数、日志、显存峰值、失败原因 |
| MIRROR | 正负样本、JPEG、截图、不同生成器 | FPR、召回、AUC/AP、分组计数与不确定性 |
| DocShield | 中文票据的金额/日期/号码字段、真实负例、已知篡改框；单模型字段抽取与加入 OCR 对照 | 框匹配、过大框率、字段完整率/精确率、输出格式与耗时；生成风险评分不当作 OCR 分数 |
| OCR/规则 | 关键字段精确匹配、字符歧义、C01–C15/G01–G08 | 字段/关系/证据定位结果、错误通过率、NEI与覆盖率 |
| 报告 | 分项结论、版本更正、图片/PDF脱敏 | 导出后文本抽取、像素检查及权限验证 |
| PDF 辅助接入 | 核心图片流程验证后，测试电子/扫描/混合页、旋转、加密、损坏、超大页 | 页级状态、文本/OCR来源、坐标回映和资源上限，复用现有材料入口 |

DocShield 输出框时使用框级评测，不将大框当作像素掩码精度。真实负例必测误报，训练样本与独立测试分开报告。上线所需误报/召回及性能门槛尚未给定，首次验证后明确验收阈值并在独立测试前固定，不看完测试结果再改口径。

代码接入后执行项目规定的 check/test/build/smoke/OpenSpec 严格校验；当前框架测试强制所有场景空白/501，启用本场景时需与组长对齐相应测试，不影响其他未实现入口。测试通过不得仅依靠旧占位断言。

## 本轮已取得的验证证据

- PP-OCRv6 medium det/rec 各 5 个文件均通过官方完整性校验；PaddleOCR 3.7.0、PaddlePaddle 3.3.0、PaddleX 3.7.2 在独立 CPU 环境加载成功。
- 两张研究票据分别提取 32 和 84 个文字区域，单图约 13.21 秒和 51.20 秒（含预处理，未做性能优化），模型加载约 1.58 秒。输出保存可见原值、四边形、识别分数、图片 SHA-256 与页码。中英混合收据读出“盐酥鸡”“鸡丝凉面”“牛肉面”及金额；两张样本不是准确率验收集。
- 服务器无 libGL，OCR 使用 `opencv-contrib-python-headless==4.10.0.84`。PaddleX 3.7.2 仅识别 GUI 包名，已在独立环境应用可重跑的包名兼容补丁，记录修改前后 SHA-256；保留其他依赖检查，不改模型算法。生产打包需显式包含这项环境适配。
- 下载工具支持 HF 镜像、官方元数据快照、断点与分段下载；7 项本地测试覆盖损坏拒绝、路径穿越拒绝、Git blob 哈希、断点合并、已校验文件复用和拒绝覆盖已有资产。Google Drive 资产仅记录自算 SHA-256，不能声称取得发布者哈希。
- OCR 损坏文件恢复测试中，第一项明确失败，后一张票据仍成功提取 32 个区域；新增输出包含模型文件哈希，检查所有四边形坐标位于实际图像范围内。
- MIRROR 完整 Phase 2 检测器已在 GPU 3 严格加载，缺失和多余参数均为零；加载约 2.51 秒，PyTorch 分配显存峰值约 3.44 GiB。GenImage ADM 与 Chameleon 共 8 张图片成功推理，插入的损坏文件失败后仍继续处理后续图片。按样本目录标签对照，默认分类在其中一张 Chameleon 真实图片上产生误报；这组小样本只验证链路，不作为准确率或阈值验收。原始证据为本地 `mirror-smoke.json`。
- DocShield 四个权重分片及其余固定版本文件均完成官方哈希校验；GPU 3 上 BF16 加载约 4.92 秒，两张研究票据处理约 13.13 秒、39.51 秒，PyTorch 分配显存峰值约 17.87 GiB。单模型默认提示词在长票据上输出 5 个异常框，其中 3 个超过原图宽度；还生成与当前可见金额不符的修改前后叙述。不能直接采用这些坐标、历史值或生成风险分作为可信核验结果。原始证据为本地 `docshield-smoke.json`。
- 同一长票据加入 84 个 OCR 区域作为证据，要求 DocShield 引用框编号、逐字引用当前值并输出 JSON。模型生成约 15.38 秒、314 token，分配显存峰值约 19.55 GiB；移除末尾模型结束标记后可解析 JSON。两项候选均引用存在的 OCR 编号，引用值包含在对应文字中，可以回到 OCR 框；但两项都漏掉要求的 `needs_rule_check` 字段，仍依据模糊/褪色推测篡改。此结果只证明协作链路可运行，结构契约未完全满足、异常判断未获独立验证，不能直接进入最终结论。原始证据为本地 `docshield-ocr-assisted.json`，输入、提示词和 OCR 来源另行留档。
- 以上研究票据来自模型相关训练数据的公开副本，且没有发布对应掩码，不能据此报告独立泛化指标或定位 IoU。OCR 文字框是文字证据位置，不自动等于真实篡改区域。脚本入口和复现方式见 [验证工具说明](../../scripts/image-validation/README.md)。
- 当前公共 `scripts/check.mjs` 禁止任何任务出现完成勾选；已完成的准备验证暂记录于此，公共规则调整仍待确认。模型加载实测不意味着页面、接口或整体验收完成，未进行 commit、push 或合并。

## 票据协作原型进展

2026-10-21 已实现[票据多方法协作原型](receipt-fusion.md)：基于图片和 OCR 版本摘要的引用检查、文字框关联、中文/英文明确版式的十进制金额核对，以及局部二次 OCR 和歧义复核队列。新报告为 `ocr-evidence-v2.json`、`docshield-visual-evidence-v3.json`、`ocr-crop-reread.json` 和 `receipt-fusion-v3.json`。

真实研究样本的正常收据两项算术通过；长票据一项显示值矛盾、一项因 OCR 歧义待复核。新版视觉提示词在两张样本上均未给出观察项，包括伪造标签样本，不能宣称视觉检出问题已解决。二次 OCR 仍读到 `9..747`，没有自动纠正。详细限制、研究版式和后续事项见上述协作文档。原型不包含已上线接口、跨材料规则全集、脱敏报告或 PDF 实现。

进一步的规则选区＋清晰局部图实验中，完整上下文回显被结构校验拒绝；精简为区域编号后，DocShield 能引用 `ocr-72` 和 `9..747`，但解释仍是数字格式问题。最终回放 `receipt-rule-guided-v2.json` 将其保留为待分类观察、注明与 OCR 歧义重合，不将它算作独立视觉证据。

最终自检：在 `image-download` 隔离环境中 31 项测试通过（7 项资产工具、24 项票据证据/算术/局部复核）；Python 编译、项目 `npm run check`、OpenSpec 全量严格校验和 `git diff --check` 通过。测试覆盖不等于业务检测准确率，未修改公共检查脚本，未执行 commit、push 或合并。
