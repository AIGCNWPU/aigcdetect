## 一、增值税发票 OCR（阿里官方读光）

请求：`POST https://dgfp.market.alicloudapi.com/ocrservice/invoice`，body `{"img":"<base64>"}`（参数名为 `img`，非 `image`）。

返回中文字段：`发票代码/发票号码/开票日期/发票金额/不含税金额/发票税额/大写金额/受票方名称/…/发票详单`。

逐字段对照（金标来自我们 10/26 真实核验记录）：

| 字段 | 金标 | 外部 API | 我们 |
|---|---|---|---|
| invoice_code | 2024330000123 | 2024330000123 | 2024330000123 |
| invoice_number | 0001345 | 0001345 | 0001345 |
| invoice_date | 2024年08月29日 | 2024年08月29日 | 2024年08月29日 |
| gross_amount | 1999.99 / 30000.00 | 同 | 同 |
| net_amount | 1999.99 / 30000.00 | 同 | 同 |
| tax_amount | 259.99 / 62.31 | 同 | 同 |
| 购方名称 | 李*娜 / 江*速 | 同 | 同 |

合计 **14/14 字段一致**（两份各 7 项）。它对完税证明返回 `430 图片和服务类型不匹配`——说明该 API 只接发票，跨材料类型不覆盖。

## 二、批量文档比对（阿里官方）

请求：`POST https://doccompare.market.alicloudapi.com/ocrservice/doccompare`，body 为 `referenceParam.docParamList[]` 与 `queryParam.docParamList[]`，每项 `{id,img}`（需 form/json 均可，图片 base64 ≤4M、最长边 ≤4096）。

返回 `doc.match_list[].match_detail[]`，每条含 `type`（modify/delete/insert）与 reference/query 两侧文字及坐标。

| 样本对 | 差异数 | 典型差异 |
|---|---|---|
| E01 vs E02（同票号不同金额） | 27 | `宁波增值税`→删除；`子普通发票`→`普通发票`；`称：李*娜`→`江*速` |
| CrossCred 同编号完税证明 | 15 | `国家税务总局南京市税务局`→`国家税务局总局开封市税务局`；税号 `9132010620230518765`→`9140200MA01Q2XWBP` |

**重要**：它输出的是**文字级 diff**，不做语义或算术判断。27 处差异中相当一部分来自版式/字号导致的切分差异，并非业务矛盾；要得到"价税合计不符"这类结论仍需规则层。这正是我们"内容核验层"的差异化依据。

## 三、发票查验（中科逸视）

必填参数（从 `x-ca-error-message` 逐次探明，**form-urlencoded**）：`invoice_number`、`invoicing_date`、`invoice_amount`，可选 `invoice_code`。

- 用合成票 E01 调用：HTTP 200 + `{"code":"CY0005","msg":"发票代码格式错误"}`
- 原因：我们的测试票是合成数电票，号码 `0001345` 仅 7 位，不满足真实票面格式校验
- 随后额度耗尽：`x-ca-error-code: B403MQ`（Api Market Subscription quota exhausted）

**结论**：验真类 API 依赖真实合规票面，与合成测例天然不兼容；它查的是"票在税务系统是否存在"，我们查"票面是否自洽"，属能力互补而非同一赛道。

## 四、身份证 OCR

端点与参数按官方文档（`image` + `configure.side`）。用 FCTM 伪造文档图和 DeepFakeFace 真实人脸调用，均返回 `463 Invalid Input - wrong category`。

**原因**：数据集内没有真实身份证样张（隐私与合规原因不采集），本轮无法验证其字段准确率与 `tamper_score`。这是一处待补测项。

## 五、证件票据 PS 篡改检测（快证签）

首轮按 `{image}` 调用，返回 `{"msg":"请输入图片","success":false,"code":400}`；按同厂商文档改为 `{base64, detectThreshold, restrictProbability}` 后，额度已耗尽（`B403MQ`）。

**未取得有效结果**，不能对其实力下结论。已把正确参数写进适配器，待补充额度后重跑。

## 六、过程中的教训（供后续评测参考）

1. **探参数会烧额度**：10~20 次的体验包在参数试探阶段就耗尽。正确做法是先读文档（或从 `x-ca-error-message` 用最小样本定位），确认一次成功后再批量跑。
2. **各商品参数风格不统一**：官方读光用 `img`；查验类 form + snake_case；篡改类 `base64`；身份证 `image`。适配器已按商品分别建模。
3. **额度是每商品独立**：五个商品各自有独立套餐，一个耗尽不影响其他。
4. **安全**：AppCode 已在会话中明文出现，建议在买家中心重置；归档只记录 URL 与响应，不含密钥。

## 七、发票查验第二轮（额度补充后，2026-11-10 晚）

补充 10 次额度后，用**真实数电票**（`23412000000052124997`，2023-11-15，价税合计 306500.00，购销方为唐河县教育装备与技术保障中心 / 唐河县欧科电器制造有限公司）做三次定向调用，一次命中，剩余 7 次保留。

请求（form-urlencoded）：`invoice_number`、`invoicing_date`、`invoice_amount`，可选 `invoice_code` / `check_code`。

| 样本 | 提交要素 | 返回 | 判定 |
|---|---|---|---|
| real-correct | 号码＋2023-11-15＋306500.00（原样） | `code=0000`，`msg=查验成功` | ✅ 验真通过 |
| tamper-amount | 金额改为 306000.00 | `code=CY0017`，`msg=发票数据不一致` | ✅ 识别金额被改 |
| tamper-date | 日期改为 2023-11-16 | `code=CY0017`，`msg=发票数据不一致` | ✅ 识别日期被改 |

成功响应的 `content` 是 base64 编码的税务票面 JSON，解码后与本方 OCR 结果逐字段对照：

| 字段 | 税务返回 | 我方 OCR |
|---|---|---|
| fphm（号码） | 23412000000052124997 | 23412000000052124997 |
| kprq（开票日期） | 20231115 | 2023年11月15日 |
| jshj（价税合计） | 306500.00 | 306500.00 |
| je（金额） | 303465.35 | 303465.35 |
| se（税额） | 3034.65 | 3034.65 |
| gfmc（购方） | 唐河县教育装备与技术保障中心 | 唐河县教育装备与技术保障中心 |
| xfmc（销方） | 唐河县欧科电器制造有限公司 | 唐河县欧科电器制造有限公司 |

7/7 一致；税务返回额外提供购销方税号（`gfsh` / `xfsh`），我方该两项未抽取，是明确的字段缺口。`jfbz` 为交付标志。

### 对 benchmark 的意义

1. **能力边界清晰**：验真类能发现"与税务记录不一致"（改金额、改日期），我们无法也不应声称覆盖；我们能在**没有税务数据源**时从票面自身发现"价税合计≠金额+税额"，两者互补。
2. **可作为交叉校验金标**：对真实票，税务返回可当独立真值来评估我方 OCR 与规则；对合成票（如 E01/E02 的 7 位号码），验真直接 `CY0005` 拒绝，说明合成测例天然不适合验真赛道，benchmark 里不能把这种拒绝计为对方失败。
3. **合成票的号码格式**导致 `CY0005`，与算法能力无关，评分时必须单列"格式/不可用"，不得算作错误。

剩余 7 次额度保留，用于后续真实票抽样或复现核验。

## 八、图片篡改识别（怜花数科）十次实测（2026-11-10）

端点 `POST https://lhtpcg.market.alicloudapi.com/image/forgery/detection`，form-urlencoded：`base64`、`restrictProbability`、`imgType`、`detectThreshold`。返回 `data.detectionResult`（fake/real）、`tamperedProportion`、`tamperedLocation[]`、`heatmap`。

样本：FCTM 伪造文档 4 张（含真值掩码，篡改像素占 5.2%）＋ DeepFakeFace 真实人脸 1 张 ＋ 豆包 AI 生成图 1 张。10 次额度全部用完（6 + 3 + 1）。

### 检测结果

| 样本 | 默认阈值 0.9887 | 阈值 0.4 |
|---|---|---|
| FCTM 伪造文档 ×4 | 全部 `real`（置信 0.444~0.499）→ **4/4 漏检** | `fake`（0.451 / 0.499）→ 2/2 检出 |
| DeepFakeFace 真实人脸 | `real`（0.321）→ 正确 | `real`（0.321）→ 正确，无新增误报 |
| 豆包 AI 生成图 | `real`（0.804，全批最高） | 未测（额度不足） |

### 定位能力

- `tamperedLocation` 在 `restrictProbability` = 0.8 / 0.3 / 0.1 三档下**始终为空数组**，未返回任何坐标。
- `heatmap` 字段解码后是**校正后的整张文档图**（755×824，带紫色底色），不是热力图；按像素统计均值 0.69、几乎全图同值，无法用于定位。
- 因此**无法计算定位 IoU**，与本方 TruFor/SEED 的 IoU 指标不可比。

### 与本方 TruFor 同图对照（本地推理，无 API 消耗）

用同一批 4 张 FCTM，`scripts/image-validation/evaluate-trufor-fctm.py`，权重 sha256 `ac1d90e3…`：

| 方法 | 分数区间 | 阈值 0.5 检出 | 0.5 时像素 IoU |
|---|---|---|---|
| 怜花 API | 0.444~0.499（默认阈值 0.9887） | 0/4 | 无坐标，不可算 |
| 本方 TruFor | 0.338~0.361 | 0/4 | 0.00（0.15 阈值下 0.021） |

**结论：FCTM 这批中文证件伪造对双方都很难**，两者在各自默认操作点下均未检出。不能据此宣称任何一方更强；差异只在分数区间（API 0.44~0.50 vs TruFor 0.34~0.36）与可调阈值行为。

### 对 benchmark 的意义

1. 该 API 的默认阈值 0.9887 极其保守，在真实篡改样本上漏检率很高；把阈值降到 0.4 后能在我们的样本上检出且不误报真人脸——但阈值是我们选的，报告里必须写清"默认 vs 调参"两套结果，不能只报好看的那套。
2. 它**不提供可用定位信息**，无法参与"篡改定位 IoU"赛道；只能进"是否篡改"二分类，且样本量（4 张伪造 + 1 张真实）不足以给出统计结论。
3. 豆包 AI 生成图给出全批最高分 0.804 但仍判 real——说明它衡量的是"PS 痕迹"而非"AI 生成"，与我们 DDA-H+ 的整图生成检测是不同任务，不应混为一谈。

## 九、图片篡改识别（jmtpcgsb 通道）十次实测：5 难 + 5 中（2026-11-10）

端点 `https://jmtpcgsb.market.alicloudapi.com/image/forgery/detection`（与 lh 通道同 AppCode 同模型：同一批图两次调用分数差 <0.001）。本轮**只测篡改**，不涉及整图 AI 生成判定。

参数：出厂默认判定阈值（不传 `detectThreshold`，即 0.9887），`restrictProbability=0.1`（仅下调区域门槛以争取坐标，不影响检测判定）。

样本：难图 5 张 = FCTM 伪造证件（含真值掩码，篡改像素 5.2%）；中等图 5 张 = DeepFakeFace 换脸（`dff-insight-0000…0004`）。全部为已确认为篡改的样本。

### 检测结果

| 图档 | 样本 | API 判定 | API 置信度 | TruFor 分数（阈值 0.5） |
|---|---|---|---|---|
| 难 | hard-fctm-0…4 | 全部 `real` | 0.431 / 0.499 / 0.444 / 0.456 / 0.431 | 0.360 / 0.358 / 0.338 / 0.361 / 0.339（全未检出） |
| 中 | medium-swap-0…4 | 全部 `real` | 0.339 / 0.351 / **0.422** / 0.335 / 0.368 | **0.578 检出** / 0.317 / **0.862 检出** / 0.367 / 0.371 |

- **API 召回（出厂阈值）：0/10**（难 0/5，中 0/5）
- **TruFor 召回（0.5）：2/10**（仅 2 张换脸检出，难图 0/5）
- 两者对 FCTM 均无效：TruFor 像素 IoU 在 0.5 阈值下为 0，0.15 阈值下仅约 0.021

### 定位输出

10 次中仅 2 次返回坐标，且都是**面积极小的孤立框**，落在 512×512 图像上只有 27×21 与 32×14 像素、置信度 0.53~0.59，与换脸区域（整张脸）不符，属噪声级输出：

| 样本 | 返回区域 | 置信度 |
|---|---|---|
| medium-swap-2 | top 417, left 142, 27×21 | 0.586 |
| medium-swap-4 | top 228, left 2, 32×14 | 0.529 |

FCTM 五张（区域真值明确为 6 块文字框）**一次坐标都没返回**。结论：该接口在本批样本上不具备可用的篡改定位能力，无法参与 IoU 赛道。

### 结论（如实表述）

1. **出厂默认阈值下，该 API 对 10 张已确认篡改图（含 5 张明显换脸）全部判 real**，置信度集中在 0.33~0.50，远低于其 0.9887 的判定门槛。这不是"图没被篡改"，而是其默认操作点极度保守、对证件/人脸域不适应。
2. **本方 TruFor 在同一批图上也只能检出 2/10**，难图全灭。因此**不能宣称我们显著优于该 API**；差异在于 TruFor 对明显换脸有一定响应（0.58/0.86），API 几乎无响应（最高 0.422）。
3. 两家在 FCTM 这类"合成证件 + 小面积文字框篡改"上都失败，说明该域是共性难点，需要针对性训练，不能靠通用模型直接套。

### 回执与额度

10 次调用均有唯一 `taskNo`（187252843242384891366923 等），全部 HTTP 200 并返回与上传图对应的 heatmap；本地账本 `budget.json` 记录 attempts=10。若控制台显示 0，请用 taskNo 与供应商核对用量归属。

## 十一、通用 AI 篡改（CocoGlide inpainting）五次实测：API vs TruFor（2026-11-10）

端点 `POST https://sdtpcg.market.alicloudapi.com/api/forgery/detection/ocr`，form：`image`（base64）、`url`。响应 `data.detection_result`（fake/real）与 `data.tampered_location[]`。

样本：CocoGlide 官方 40 对中的 5 张 GLIDE inpainting 伪造图，**按 TruFor 分数分层抽取**（第 1、10、20、30、40 名），不是按 API 结果挑选。图像 256×256 PNG，base64 89~202 KB（未压缩，低于接口 1 MB 硬限；其建议值 100 KB 未强制）。

### 逐张结果

| 样本 | TruFor 分数 | TruFor 检出 | TruFor 像素 IoU | API 判定 | API 区域 | API 区域 IoU |
|---|---|---|---|---|---|---|
| 15497 | **0.9998** | ✅ | **0.961** | real | 0 | — |
| 368684 | **0.7156** | ✅ | **0.557** | real | 0 | — |
| 548506 | 0.3494 | ❌ | 0.048 | real | 1 | 0.024 |
| 96960 | 0.2311 | ❌ | 0.390 | real | 0 | — |
| 228436 | 0.0999 | ❌ | 0.000 | real | 0 | — |

**召回：API 0/5，TruFor 2/5。** API 连 TruFor 给出 0.9998、像素 IoU 0.961 的明显 inpaint 图也判 `real`。

### 一处接口自相矛盾

样本 548506 返回了一个区域，置信度 **0.828**（高于其文档中 0.8 的常见阈值），但整体判定仍是 `real`。即区域分支与整体判定口径不一致，该区域对真值掩码的 IoU 仅 0.024，属噪声。

### 局限与不能下的结论

1. **域不匹配是客观存在的**：该端点路径含 `/ocr`，文档面向证件/票据（返回 `orderNo`、区域坐标以像素计），CocoGlide 是自然照片的 GLIDE inpaint。用它评自然图像属**跨域测试**，对厂商不完全公平，报告中必须标注。
2. **尺寸建议未满足**：其文档建议 base64 压缩至 100 KB 以内，我们保留了原图（89~202 KB）。是否影响精度未验证——额度已用尽，无法做同图压缩对照。
3. 5 张样本量不足以给出统计结论（区间宽），只能作为方向性证据。

### 结论

在**通用 AI 局部重绘（inpainting）** 这一任务上：本方 TruFor 在能检出的样本上不仅判定正确，定位 IoU 达 0.56~0.96；该 API 在同样 5 张上全部判 real，无可用定位。但这不能推广为"API 全面更差"——需在证件/票据域、且按建议压缩输入后复测，才能做同类比较。

## 十二、图片修改线索检测（aips /psdect）百次额度实测：三类 ×（10 难 + 10 易）+ 30 张真实对照（2026-11-10）

端点 `POST https://aips.market.alicloudapi.com/psdect`，form `src`（图片 base64）。响应实际结构为 `{status, Threshold, position:[x1,y1,x2,y2]}`——**`Threshold` 字段承载 0~1 的分数**，`position` 每张都返回（疑似默认框）。按厂商建议以 ≥0.8 作为"较大 PS 痕迹"的判定参考。

100 次额度分配：人脸 20、票据 20、通用 AI 20、票据压缩复测 10、真实图误报对照 30。

### 汇总

| 类别 | 组 | 样本 | 召回 | 误报率 |
|---|---|---|---|---|
| **人脸** | 简易（DeepFakeFace 换脸 ×10） | 10 | **8/10 = 0.80** | — |
| 人脸 | 困难（局部重绘 ×10） | 10 | **7/10 = 0.70** | — |
| 人脸 | **真实人脸对照 ×10** | 10 | — | **7/10 = 0.70** |
| **票据** | 简易（真实票面同图复制粘贴，GT 明确 ×10） | 10 | **0/10** | — |
| 票据 | 困难（FCTM 小框篡改 ×10） | 10 | **0/10** | — |
| 票据 | 压缩复测（JPEG ≤210KB ×10） | 10 | **0/10** | — |
| 票据 | 真实票面对照 ×10 | 10 | — | **0/10** |
| **通用 AI** | 简易（CocoGlide，TruFor 0.72~1.00 ×10） | 10 | **1/10** | — |
| 通用 AI | 困难（CocoGlide，TruFor 0.10~0.22 ×10） | 10 | **0/10** | — |
| 通用 AI | 真实照片对照 ×10 | 10 | — | **0/10** |

### 关键结论：人脸项的数字是假的

人脸召回 0.80 / 0.70 看似不错，但**真实人脸误报率同样是 0.70**。也就是说它对"人脸"这个类别近乎恒定输出高分，区分能力约等于零。真实人脸分数分布：`1, 0.94, 1, 1, 0.936, 1, 0.410, 0, 0, 1`。

若按平衡准确率计算：人脸 ≈ (0.75 + 0.30)/2 ≈ **0.53**，与随机猜测无异。

### 票据与通用 AI：恒定为 0

- 票据 20 张篡改（含 GT 明确的大块复制粘贴）全部 `Threshold=0`；**压缩到 90~210KB、转 JPEG 后重测 10 张仍全部为 0**，排除了尺寸/编码限制的解释。
- 通用 AI 20 张中仅 1 张（TruFor 0.9415 的那张）给出 0.809，其余 19 张为 0——包括 TruFor 判 0.9998 的明显 inpaint。
- 这两类真实图也是 0，说明它不是"偏保守"，而是**该域完全没有响应**。

### 分数形态

70 次检验中出现过的分数只有 15 个离散值：`0, 0.047, 0.382, 0.410, 0.419, 0.428, 0.8, 0.809, 0.818, 0.836, 0.854, 0.891, 0.936, 0.94, 1`。其中 `0.8090770036` 在两张不同人脸和一张 CocoGlide 图**完全相同**，`0.8` 也重复出现。这不像连续置信度，更像分段/桶化输出，进一步削弱"分数可作阈值调节"的解释力。

### 结论

- 该 API 在**票据**和**通用 AI 篡改**两个赛道实测无效（0/20、1/20），且非尺寸原因。
- 在**人脸**上它对篡改图与真实图给出一致的高分，**区分度不成立**，不能用于业务判定；厂商文档也明确"不能只凭一个分数确定图片真假"，实测印证了这一点。
- 三条赛道的对比表应如实填写：本方 VLAForge / TruFor 在有真值的数据上给出可解释的分数与定位，该 API 在三类上均未表现出可用区分度。

### 样本构造声明

票据"简易"组为**构造样本**：取真实数电发票与 CrossCred 完税证明，在同一张图内做区域复制粘贴（copy-move），粘贴框即真值。构造脚本与参数在 `datasets/documents/psdect-easy-20261110/manifest.json`，非真实业务篡改，仅用于探测模型对明显 PS 痕迹的敏感性。

## 十三、文档篡改：SEED 与 API 补充验证（2026-11-10）

应用户要求，文档篡改域改用 2.3 服务链路的 SEED 模型验证，并与外部 API 同图对照（TruFor 结果保留作参考）。脚本 `scripts/image-validation/evaluate-seed-batch.py`，直接使用服务态适配器与原生概率图，未调参。输出在 `runtime/replay/seed-{fctm,doc-easy,doc-clean}-20261110/`。

### SEED 三组结果

| 组 | 样本 | 判定（分数≥0.5） | 分数区间 | 定位 IoU@0.5 |
|---|---|---|---|---|
| FCTM 小框文字篡改 | 10 | **10/10** | 0.969~0.995 | 均值 0.071 |
| 构造 copy-move（真票贴块） | 10 | **10/10** | 0.981~0.998 | 均值 0.084 |
| **干净文档对照（真实发票/完税证明）** | 10 | **10/10** ⚠️ | 0.857~0.996（均值 0.954） | —（无真值；区域数 22~33 个） |

### 关键结论：SEED 判定在文档域无区分度

篡改文档 20/20 报高分，**干净文档同样 10/10 报高分**。平衡准确率 =（100% 召回 + 0% 特异度）/2 = **50%，与随机等价**。SEED 的图级分类头对"文档类图像"近乎恒定输出高分，不能作为文档篡改判定依据。

定位层面：篡改样本 IoU@0.5 仅 0.07~0.08，且干净文档上也产生 22~33 个候选区域——区域标记在文档域同样不具备证据力。这解释了 2.3 服务中 SEED 阶段常返回数十个候选区的现象；前端"疑似修改位置，需结合原图与字段复核"的措辞与该实测一致。

### 文档篡改域三方对照（同图）

| 方法 | 篡改判定 | 干净误报 | 定位 IoU | 结论 |
|---|---|---|---|---|
| SEED（我方 2.3 链路） | 20/20 报"有" | **10/10 报"有"** | 0.07~0.08 | 无区分度 |
| 外部 API（psdect） | 0/20 报"无" | 0/10 | 无输出 | 无响应 |
| TruFor（我方 2.1 链路，参考） | 3/10（copy-move）/ 0/5（FCTM） | 未单独测文档 | ≈0 | 接近无响应 |

**总结：文档篡改域目前没有任何一方（含我们自己的两个模型与外部 API）具备可用的判定或定位能力。** SEED"全说是"、API"全说否"、TruFor 接近"全说否"——三种失效模式不同，但都不可用。该域的可信结论仍来自内容层（OCR 字段 + 规则 + 智能核验）。要建立文档视觉篡改能力，需要文档域微调（FCTM/CrossCred 可作训练集），通用权重直接套用已被本组实验否定。

## 十四、修正：CrossCred 图像自带脱敏涂改，SEED"干净对照"口径更正（2026-11-11）

用户核对 CrossCred 原图时发现图上有明显色条/涂块。经查该数据集 README：**全部图片在开源发布前经过人工脱敏，且按审批要求刻意保留涂改痕迹**（"clear processing traces have been retained to demonstrate that desensitization has been applied"）。因此：

1. CrossCred 图上的框/色条是**脱敏标记**，既不是数据集的异常标注，也不是伪造篡改；其内容异常（同编号不同税号等）只记录在 eval_set.csv，不在图上标框。
2. 第十三节 SEED"干净文档对照"中的 8 张 CrossCred 图**并非视觉干净**——它们含有大面积真实存在的局部涂改（脱敏块）。SEED 对这 8 张报警不能全部计为误报。
3. 真正未经任何修改的只有 real-doc-00/01（E01/E02 数电票渲染图），SEED 对其同样报 0.9971/0.9945。但 n=2 且这两张本身是合成渲染票（非扫描件），证据不足。
4. **结论更正**：第十三节"SEED 在文档域平衡准确率 50%"的表述过强，应改为："SEED 对视觉含涂改的文档（含脱敏块）与 FCTM 篡改文档均报高分；对仅有的 2 张渲染发票也报高分，但缺乏真·未修改扫描票据的对照，文档域区分度尚未定论，需补充干净扫描票据对照后重测。"

后续动作：以真·未修改的扫描票据（可从合规渠道的普通票据扫描件或自建渲染-扫描对照）重做干净对照，再定 SEED 文档域结论。
