# 中文材料真实语义核验：本轮结果复核（2026-10-26）

## 1. 结论与证据边界

本轮 8 次真实请求均成功完成，但最终事项判断全部为 `needs_more_information`，没有一次返回 `issues_found`，8 个 `warning` 全为空。**这不能称为“8 次业务审核通过”，也不能称为“8 次成功发现矛盾”。** 原文模式能识别若干实际内容差异，其中发票请求还明确识别了单份票面内部的算术不一致；这些发现没有成为最终结构化告警。租赁合同还有输入中已经提供、却没有被指出的金额条款冲突。

本报告是同一项目、同一轮实验中的代理复核，采取另一个审核视角逐项读取请求、响应和原图，**不是独立专家标注，不是盲测真值，也不是新一轮模型实验**。复核没有发起任何新的模型 API 请求。作者注释只作为待核查假设，不直接视为正确答案。

复核范围：

- CrossCred 的 g1、g34、g72、g74，每组前两份材料，共 8 张不同原图；每组原文、脱密两种请求，共 8 次响应、16 个材料输入实例。
- 逐项读取对应 `package.json`、`result.json`，对照组说明 `groups.json` 与 `ocr-manifest.json`，查看这 8 张原图；8/8 原图 SHA-256 与清单一致。
- g1 全组有 3 份、g34 全组有 5 份，本次语义请求只包含各自前两份；不把全组注释中的全部差异都当作本次请求应当发现的差异。
- 仅检查材料内容与语义结果。不据此评价 MIRROR、SEED 定位精度、发票官方查验结果、最新政策适用性或真实世界法律效力。

本报告只使用样本代号和非身份类的金额、日期示例，不复制原始姓名、证件号码、邮箱、企业名称或机器绝对路径。

## 4. 对照原图与作者假设

### 4.1 g1：承诺函与账户列表

两份图示承诺函中的显示身份、承诺期间、落款日期相同，账户列表不同：第一份列 3 个邮箱，第二份列 5 个，所列集合没有重合。原文响应成功描述了这个差异。

作者注释把同一身份应当对应相同账户列表作为判错前提，这个前提不能直接成立。个人或公司可以拥有多个账户，也可能针对不同账户分别出具承诺、追加账户或更新清单。只有补充“本函必须列出同一主体在同一时点的全部账户”“相同版本不得改变清单”等约定后，才适合判断冲突。当前响应没有把多邮箱直接判为错误，这一点应保留。

第三条关于禁止交易类型的文字，在两张原图中都存在。原文请求 m1 的相应片段没有进入可用证据，m2 则保留在 `e52`；响应据此说成条款文本差异。其错误是**把输入未提供转成原材料不同**，不是无中生有地编造整个条款。更准确的表述应是“第一份该条未被完整提取，暂不能比较”，再回到本地原图补 OCR。

承诺函不一定应当具有合同编号。补件建议应围绕承诺对象、账户归属、清单范围、版本与签署情况，而不是统一要求所有材料都有交易合同或凭证编号。

### 4.2 g34：发票内部算术与跨版本差异

选入请求的两张图显示相同发票代码、号码及开票日期。全组作者说明涉及日期等多种差异，但**本次两张图日期相同**；未发现日期差异不能记为漏检。票面交易内容不同这一点，原文响应已有识别。

对选入图示数字复算：

| 单份样本 | 图示关系 | 复核结果 | 模型是否指出 |
|---|---|---|---|
| g34-m1 | 金额 1,999.99 + 税额 259.99，价税合计却为 1,999.99 | 相加为 2,259.98，和所列合计不一致 | 是，但只在解释中，未告警 |
| g34-m2 | 金额 30,000，税率 13%，税额 62.31 | 按图示金额与税率直接计算为 3,900，与 62.31 不一致 | 是，但只在解释中，未告警 |
| g34-m2 | 金额 30,000 + 税额 62.31，价税合计为 30,000 | 相加为 30,062.31，和所列合计不一致 | 没有明确指出这一条 |

以上是针对图示字段之间关系的核验，不是对真实纳税义务、税收优惠适用或票据真实性的权威认定。m1 的税率计算还有分位舍入问题，本轮不将一分钱差额另计重大错误，避免没有明确容差的扩大判错。

原文响应引用 m2 的 `e81`、`e82` 来说明“金额 30,000”：`e81` 实际是单价 15,000，`e82` 是金额 30,000。金额结论没有错，但引用集合混入了不同列，应区分单价、数量、金额的字段关系。脱密响应已经无法明确 15,000 与 30,000 的关系，进一步说明无表格结构的文本块不适合稳定完成算术审核。

跨材料可能有更正、红冲、版本或识别误差，需要继续核实；但单份内部的加总不一致，不以确认两张材料属于同一交易为前提。合理输出应同时保留“票面金额关系需要核对”的明确提醒和“版本关系未确认”的待补项，而不是用一个 NEI 覆盖二者。现有响应结尾把 `evidenceComplete=false` 和关联材料缺失用于不报告确定矛盾，造成这一层混淆。

### 4.3 g72：购销合同的版本一致性

两份图中订单标识及甲乙方相同；交易日期分别为 2024-10-02 和 2024-10-10，付款方名称不同，金额分别为 499.99 和 700。原文响应成功指出这三类实际差异，且把分期、补单、变更作为待验证可能性，没有直接当作既定事实。

两张原图中的规格均为 2 米 × 1.5 米 × 2 米。第二份规格没有进入本次有效文本证据；响应解释仅说“未见对应规格型号”，但摘要升级成“规格型号存在差异”。这里应标记“第二份规格提取不完整”，不能记为真实合同差异。

本组确实需要核实版本、变更约定及付款背景，NEI 可以描述最终关系判断；同时应独立显示已确认的日期、付款方与金额差异，方便用户有针对性地补件。不同日期或不同付款方本身不能直接证明篡改。

### 4.4 g74：租赁合同的身份对应与金额条款

原文响应发现两份材料中的承租人证件编号相同、显示姓名不同。这个事实适合形成“身份对应待核实”提示，原因可能是录入、识别、版本或身份信息变更；不能仅凭它确认伪造。身份属性是否一致与两份合同是否为同一交易是不同问题，不宜统一用“缺少同一交易依据”终止比较。

两张原图都显示相同的占位社区名和房间号。m1 的地址内容未完整进入 OCR 证据，响应摘要却说 m1 地址缺失。正确边界是“本次输入未完整提取地址”。占位地址即使相同，也不能证明现实中确为同一房屋。

**另有单份合同内部问题未被指出：** 两份图均写月租 1,700 元、押一付一，首付款含一个月押金和一个月租金，却列首付 2,400 元。在没有折扣、抵扣或已付款条款的现有输入下，应核对 1,700 + 1,700 = 3,400 与 2,400 的不一致。模型输入已有必要数字及含义：m1 见 `e17`—`e21`，m2 见 `e73`—`e77`，因此不能把这次漏检完全归因于隐私过滤或 OCR 未提供。

这里应输出“首付款与押付约定不一致，需核实是否另有抵扣或补充约定”，不需要先断定跨文件属于同一交易，也不需要直接下“合同被篡改”的结论。

## 5. 为什么八次都返回 NEI

可以从请求和代码确认的事实：

1. 每个请求只有一个跨候选材料的 `q1`，均为 `relationship_context_review`；不是先逐份检查内部一致性、再独立检查关联关系的多事项任务。
2. 8 个包均 `relations=[]`、`localFindings=[]`、`focusEvidenceIds=[]`，事项均 `evidenceComplete=false`。原生本地关联没有自动建立，本轮是按数据集作者候选组补充的诊断请求，不能称为生产流程已自动识别全部关系。
3. 提问强调“没有足够关系证据不得报告确定矛盾”。背景允许核查单份内容，但没有把单份算术检查拆成独立、有焦点的事项。
4. 四个脱密包大量删除整块文本，g1/g74 几乎无实质内容；它们的 NEI 是输入不足的直接后果。
5. 本轮未提供政策依据、未请求政策检索，地区未指定。因此不能据此声称已验证最新地方政策理解。
6. `semantic-review.js` 的响应校验要求 `issues_found` 必须有非空警告，只有 `reasonable` 才要求证据完整。**`evidenceComplete=false` 没有在程序上禁止 `issues_found`。** 所以“全部 NEI 是校验器强制的”这一解释不成立。

根据上述事实，合理推断是：统一关系问题与较强的关联不确定性约束，使模型把不同层面的不确定性合并处理；又没有本地算术发现、明确字段关系和单份审核事项对其施加具体任务。该推断不是提示词消融实验结论，仍需在修正方案后用固定样本验证。
