# 中文材料本地内容核验：开发回归与待验收记录

日期：2026-10-26。

## 目标和数据边界

本轮先补齐已冻结真实中文样本的本地核验，不调用外部API。目标是区分“文字已识别、字段未提取”“字段已有但规则未执行”“规则已经发现不一致”“需要业务背景确认”四类问题，并保留计算依据。

初始输入为既有CrossCred六组16张原始图片及已完成的PP-OCRv6结果：税收完税证明2张、账户承诺函3张、增值税电子普通发票5张、常住人口登记卡2张、购销合同2张、房屋租赁合同2张。原图哈希、OCR输入哈希和冻结清单逐一验证。原实验保持不变，缺失文字不以作者答案人工补齐。

这是依据同批数据集优化规则的开发回归，不是独立测试集、随机抽样或泛化准确率。作者对“相同身份下账户列表必须相同”等前提只用于明确标注的基准对照；生产平台应先确认承诺清单的完整性、时点和口径。

## 可复现执行

新脚本：`scripts/image-validation/evaluate-local-content.mjs`。

```bash
node scripts/image-validation/evaluate-local-content.mjs "$AIGC_PLATFORM_ROOT" "$AIGC_PLATFORM_ROOT/runtime/replay/local-content-20261026/v1"
```

输出路径必须是平台runtime中的新目录，已存在则拒绝覆盖。源目录固定为已冻结的`runtime/replay/chinese-live-20261026`。脚本禁止`fetch`，不读密钥、不设置真实提供者。输出含原图副本、完整OCR文字与坐标、字段、规则状态与证据、用户汇总、作者标注独立对照、JSON和可直接打开的HTML。原文含个人信息，仅在本地查看，公开文档不复写这些信息。

为覆盖作者完整组00，单独冻结追加4张完税证明的manifest和真实OCR，保持旧16张记录不变。完整复跑可添加第三参数`EXTRA_OCR_JSON`；脚本要求同目录存在`extra-ocr-manifest.json`、4张成功结果及一致模型资产摘要。本轮完整目标由16张扩为20张，字段数同时报告“相同原16张”和“新增4张”，避免将扩样数量当成提取改进。

执行时不把作者标注、预期错误或手工关系传入`extractOcrMaterial`、`evaluateReview`。分组、核心材料选择和功能目标由冻结评估方案给定；新增的“共享显示标识”关系只是可追溯内容候选，不能伪装成用户确认的同一交易。

## 评价方式

分别统计业务字段数、零字段文件数、有效比较候选、本地PASS/FAIL/WARN/NEI、用户问题提醒和未覆盖维度。OCR置信度仅描述识别分数，执行等级仅描述证据充足程度，两者都不能解释为真实性概率。

脚本按`comparedKey`和证据字段生成作者检查项的候选匹配线索，输出`machine_candidate_requires_manual_confirmation`或`not_matched_by_field_key`。这些线索不自动作为准确率；须核对比较范围、OCR值、角色、例外与真实计算后，才能记录命中或遗漏。特别注意组34的日期差异涉及5张整组，不能重复上轮只给API前2张却以整组答案评分的问题。

## 作者标签范围复核

- 组00原始作者组6张，旧实验仅冻结前2张。前2张包含机关、纳税人、识别号差异，但填发日期、税种、税期和入退库日期无对应差异。追加完整组之后才能评价这4个维度，不能将旧子集未出现的异常计为漏检。
- 组34原始作者组5张，全部已包含。2026-10-26逐张查看5张原图确认，其开票日期均为2024年8月29日。作者“日期不同”这一条与当前可见图像不一致，单列为标注争议，不强行制造日期冲突。其他4个内容差异维度正常核验。
- 组34五张的价税合计均显示为不含税金额，而另有正税额，应逐张发现加法矛盾。第2和第5张的税率税额存在大幅矛盾；第3和第4张的差异只有分级，应单独记录舍入容差，不与大额错误混算。

## 实测结果

原16张基线已于本轮脚本真实运行：17个结构字段、9张零字段、0条明确FAIL、0条用户提醒、0条自动候选。API调用、模型调用、模拟提供者调用、网络尝试均为0。基线输出：`runtime/replay/local-content-20261026/v0-baseline/`。

第一轮新规则复跑`v1`（仍为原16张）结果：140个业务字段、0张零字段、10条共享标识候选、63条FAIL、2条WARN。数量增加本身不代表准确率，逐条复核如下：

|组|真实发现及边界|
|---|---|
|00|相同证明编号下的机关、纳税人名称、识别号3类差异已发现。其余作者维度须扩全6张后评价。|
|01|账户集合差异已产生2条WARN，分别比较核心材料与其他2份。3条身份号格式FAIL另计：原图本身为17位，OCR并未漏字；与作者注释18位值不同。这些格式异常不能算账户差异的命中。|
|34|作者可见的购买方、商品服务、净额、价税合计4类差异已发现；日期均相同，未制造日期冲突。5张的净额加税额矛盾均发现；第2和5张有明显税率税额问题，第4张超1分容差的小额差异单列。第3和4张原图大写金额也与小写不同，规则发现正确。10条代码/号码格式FAIL来自原图非标准合成编号，不能与作者内容异常混算。|
|43|同显示身份号码对应姓名不同，已发现。另有合成身份号校验位异常，独立统计。|
|72|同订单号下日期、付款方、金额差异3类均已发现。没有将规格中X和×的OCR差异误作规格冲突。|
|74|同承租人标识对应姓名不同已发现；第二张首付组成矛盾已发现；第一张同一矛盾仍NEI，找到跨OCR块条件丢失的真实漏检并回报修复。|

首轮审查确认的逻辑漏检：第一张租赁合同的组成字段值已完整提取，但规则只看最后一个OCR文字块的`source.observedText`，没有包含前一块“其中包括”；应检查完整绑定的证据块或经过验证的提取值。首付应为1700×(1+1)=3400元，原件写2400元。修复后必须再次回归，两张都应保留明确计算证据。

完整20张及修复后结果待追加OCR完成。模型模拟另行明确标注，不计真实推理能力或真实API效果。

## 第二轮完整20张回归

输出：`runtime/replay/local-content-20261026/v2/`。与上一轮原图、作者标签均未改动，只追加了原作者组00其余4张的真实OCR，并应用租赁跨块修复及税表列提取。

- 20张共183个字段；同样原16张为147个字段，新增4张36个字段。0张零字段，14条标识候选。
- 79条FAIL、2条WARN、81条用户提醒。以上为执行条目数，含同一问题的多个材料/字段对、非标准合成编号格式，不是79种独立错误。
- 两张租赁合同首付款矛盾均已明确发现，保留1700×(1+1)=3400、实际2400的计算证据。
- 完税证明税表已提取税种、入退库日期、实缴金额数组，部分材料还有完整税期。入退库日期差异已命中；核心材料的税期因真实OCR碎片错误未完整提取，尚未比较出其他完整材料之间的税期差异。此项仍是漏检，应通过同标识簇内逐字段选完整代表的线性比较修复，不能凭作者答案修改OCR。
- 追加4张原图视觉复核：填发日期仍全部相同，税种序列也相同，因此组00作者上述两条与完整可见图像不一致。连同组34日期，共3条单列标注争议。作者共18个维度，其中15个在完整本地样本中存在可见差异；本轮命中14个，税期维度仍未命中。账户维度生产输出WARN，按作者基准可视为差异已发现，不能宣称业务违规已经确认。
- 组00第3张实缴金额两行与核心材料不同，肉眼原图也确实不同，不是提取器漏掉千位。这是作者未单列的额外可见差异。
- API、模型和网络调用仍均为0。本轮未改变整图检测或定位模型，未重新评价SEED/MIRROR。

下一轮仅在确认修复有新变化后复跑，并保留本轮结果。前端生产核验未通过该静态查看页面完成端到端上传验收；该页面展示真实规则输出，便于逐图复核。

## 第三轮与误报审查

输出：`runtime/replay/local-content-20261026/v3/`。补入同编号簇内逐字段参考比较：核心材料某列不完整时，保留核心NEI，另选该簇内完整材料作此字段的参考，标记`referenceComparison`、`referenceMaterialId`、`coreMaterialId`，维持星形比较。

本轮20张、183字段、14候选，82条FAIL、2条WARN、84条提醒。15个可见作者维度已全部出现检查线索，但审查发现其中1条额外税期比较误报：第2张与第4张的税期日期相同，只因第2张OCR遗漏两处“至”，直接比较原始字符串将其判为不同。第2张对第3和第6张的税期差异则真实存在。此轮不能因“作者维度都命中”就宣称规则无误。

处理方向：比较明确识别出的两个合法日期，允许格式分隔符差异，保留原OCR证据；不能为第1张多识别出的“1”静默补写答案。此修复和浏览页的可读金额计算输出将另存第四轮，不覆盖前面实验。
