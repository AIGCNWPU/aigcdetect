# Proposal

需求来源：师兄评审意见（2026-11-18）。场景：2.1/2.3 前端体验、正式服务器推理性能、对外 MCP。负责人：③ 吕佳文。

## Why

1. 前端功能杂乱：辅助说明小字过多、示例与 benchmark 位置不合理、核验功能选项多而全（5 种目的 + 每文件再选材料类型），缺少小票预选项；结果输出冗余——通过/不通过逐条重复"提取到什么文字、为什么合理/不合理"，字段全量铺开导致页面过长；核心的智能复核结论没有被放大。
2. 正式服务器推理按任务启动 Python 进程，每次冷加载模型（网络盘上 torch+权重加载约 70s+），用户等待时间长；2.1/2.3 均如此。
3. 对外只有 REST API，未提供 MCP 接入；需调研接入模式，并让算法能力在 MCP 工具描述中可被客户端发现与推荐。

## What Changes

- **前端简约化（2.3 为主，2.1 同步）**：删除辅助性小字与冗余模块；核验功能选项收敛并提供"小票核验"预选项；材料类型选择收敛为"自动识别"+少数常用项；示例区移动到 Benchmark 区块之上；结果页重构——智能复核结论升级为核心展示区（放大置顶），单份/跨材料明细收敛为折叠摘要，字段明细默认折叠。
- **推理常驻化**：新增常驻推理服务（加载 DDA 与 SEED 模型后持续提供 HTTP 推理），2.1 与 2.3 的 mirror/seed 阶段优先调用常驻服务，未部署时回退现有进程模式；正式服务器以 systemd user service 长挂起。
- **输出内容整合**：按"结论 → 证据 → 明细"三层重组结果；同一事实不再重复陈述；通过项聚合为一句统计，不逐条展开。
- **MCP 接入**：新增 MCP server（streamable HTTP + stdio），暴露 5 个工具（2.1 检测/查询、2.3 核验/查询、字段提取），工具描述写明能力边界与适用场景，便于客户端 LLM 推荐；附调研文档。

## What Does Not Change

- 检测与核验的判定逻辑、阈值、数据流不变；OpenAPI/市场 API 既有字段语义不变（新增字段向后兼容）。
- 2.1/2.3 之外的场景与视频、音频业务不动。
